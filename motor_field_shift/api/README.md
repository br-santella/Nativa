# Field Shift API

HTTP API (FastAPI) of the Field Shift **crop-rotation** recommendation engine. Given an area
(demo field, GeoJSON polygon or lat/lon point), it returns a **diagnosis** (terrain, soil,
crop history, climate, yield) and a **ranking of rotations** with a 0 to 1 score, an estimated
margin in BRL/ha and an explanation card per option. A rotation is a pair **(summer crop, second-window
crop)**: summer `soja` or `milho_verao`; second window with 11 options (the original 7 + sorghum, off-season beans,
forage radish and oat + radish).

The recommendation follows a **per-stage flow**: the farmer says the current rotation (`rotacao_atual`, required) and, optionally, the
stage of the summer crop (`estagio_verao`) or the expected harvest date (`colheita_prevista`). The engine estimates the harvest, derives the
sowing date of the second window from it and answers two questions in two blocks: **`agora`** (what goes in after this summer harvest, same
summer crop as the current rotation) and **`proxima_safra`** (what to change in the next season, other summer crop). Each item carries
`ganho_vs_atual`, how it improves (or worsens) production against the current rotation.

Field names, ids and error codes are in Portuguese, as defined in the code.

**Scope:** the whole state of Paraná (399 municipalities, IBGE code 41). Any area outside it returns
**422** with `{"erro": "fora_da_regiao"}`.

## How to run

```bash
uv sync
uv run uvicorn field_shift_api.main:app --app-dir api --reload
```

- Swagger (with pre-filled examples): <http://127.0.0.1:8000/docs>
- ReDoc: <http://127.0.0.1:8000/redoc>
- OpenAPI JSON: <http://127.0.0.1:8000/openapi.json>

On startup the API calls `service.warm_up()` (preloads the data). If data is missing, it starts
anyway and `GET /health` responds `"status": "degradado"` with the reason in `detalhe`.

Tests: `uv run pytest` (unit tests; the engine tests marked `needs_data` are skipped when `data/` is missing) and `uv run pytest -m integration` (real service and data in `data/`).

## Endpoints

| Method | Route | Description |
|---|---|---|
| GET | `/health` | Service status and whether the data loaded |
| GET | `/v1/opcoes` | Summer and second-window crops, combinations (rotations), sowing dates, criteria, default weights, income references, region, demo fields |
| GET | `/v1/talhoes/demo` | List of demo fields |
| GET | `/v1/culturas/fichas` | Agronomic crop sheets of `catalog/crops.yaml` (ranges with unit and source) and the engine crop -> sheet map |
| POST | `/v1/diagnostico` | Full diagnosis of the area |
| POST | `/v1/recomendacao` | Ranking of rotations (and, optionally, the diagnosis) |
| GET | `/v1/clima` | Shortcut: only the diagnosis `clima` block for a point |
| GET, POST | `/v1/contexto` | Current conditions (informational): ENSO, SMAP soil moisture, MJO, pest outbreaks. Does not change the ranking or the score |

### Response language (`lang`)

Every endpoint answers in **Brazilian Portuguese by default** and in **English on request**:

| Priority | How | Example |
|---|---|---|
| 1 | `lang` query parameter (`pt-BR` or `en`; `en-US`, `pt` etc. also accepted) | `POST /v1/recomendacao?lang=en` |
| 2 | `Accept-Language` header (first supported language by quality) | `Accept-Language: en-US,en;q=0.9` |
| 3 | default | pt-BR |

An unknown value falls back to pt-BR. The response carries `Content-Language` (`pt-BR` or `en`) and `Vary: Accept-Language`.

Only the **texts** change (card lines, warnings, reasons, descriptions, error messages). JSON keys, ids/slugs (`soja__milho_safrinha`,
`milho_verao`), enum values (`nivel`, `origem`, `status`, `erro`), dates, numbers and the response shape are identical in both
languages, so a client can switch language without changing its parsing. Numbers written inside English sentences use the
English separators (`R$ 2,366/ha`, `0.82`). The OpenAPI schema (`/docs`) stays in Portuguese.

The engine always writes pt-BR; English is produced at the edge of the API from the template catalog
`src/field_shift/i18n/en.json` (see "Translations" below), so the pt-BR response is never affected by it.

```bash
curl -s -X POST "http://localhost:8000/v1/recomendacao?lang=en" -H 'Content-Type: application/json' \
  -d '{"area": {"talhao_id": "72638"}, "rotacao_atual": "soja__milho_safrinha", "estagio_verao": "enchimento_graos"}'
```

#### Translations

- `uv run python scripts/i18n_extract.py` extracts every user-facing Portuguese text of the engine/API code and of the
  reference data (`data/ref/*.json`, `catalog/vocabulario.yaml`) as a template (`{0}`, `{1}`... where the code inserts a value)
  and adds the new ones to `en.json` with `null`; write the English and run the tests. `--prune` drops templates no longer used.
- `tests/test_i18n.py` fails when a template has no English, when the placeholders differ, or when the code has a text that is
  not in the catalog. `tests/golden/en/` holds the English responses, checked against the pt-BR ones (same keys, ids and numbers).
- Texts assembled from pieces (a sentence with a list, a line whose wording depends on a condition) are built with
  `field_shift.i18n.Msg("... {0} ...", value)` and `Join(items, ", ", last=" e ")` instead of f-strings/concatenation: they are
  the same pt-BR string, but keep the template, so the English is rendered from the template and the translated values. Routes
  return through `i18n.localize(...)`, which does this while those objects are still alive (before JSON serialization).
- Bibliographic titles (Embrapa, papers) and official names (ZARC crop names, ordinances) are kept as published.

### `area` object (shared by `/diagnostico`, `/recomendacao` and `POST /contexto`)

Provide **exactly one** of the three forms.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `geometry` | GeoJSON object | one of the forms | n/a | Polygon, MultiPolygon or Feature, EPSG:4326 (lon, lat). Max. 5000 ha |
| `lat` + `lon` | number | one of the forms | n/a | Point; becomes a 1000 m x 1000 m square (~100 ha, UTM 22S). Provide both |
| `talhao_id` | string | one of the forms | n/a | Demo field id (e.g. `"72638"`) |

### `GET /health`

Output: `status` (`ok`/`degradado`), `dados_carregados` (bool), `versao`, `detalhe` (reason, if degraded).

### `GET /v1/opcoes` and `GET /v1/talhoes/demo`

No inputs. `/opcoes` returns:

- `culturas_verao[]` and `culturas_segunda[]`: `id`, `nome`, `tipo` (`grão`, `cobertura` or `pousio`), `descricao_curta` and `ficha` (id of the crop sheet in `GET /v1/culturas/fichas`, or `null` when the catalog has no sheet for that crop). These are the closed enums of `rotacoes`. Each summer crop also carries `estagios[]` (`id`, `nome`, `dias_ate_colheita`: the valid values of `estagio_verao`, with the typical days to harvest) and `colheita_catalogo` (dd/mm assumed when no stage or harvest is sent).
- `estagios_fonte` (source and caveat of the stage estimates) and `dias_preparo_2a` (minimum days between the summer harvest and the second sowing; 0, no-till).
- `combinacoes[]`: every pair (22), with `id` (`"<verao>__<segunda>"`, e.g. `soja__milho_safrinha`), `id_legado` (old slug, only for the original 7),
  `nome`, `verao`, `segunda`, `valida` (false if the pair is always eliminated, such as soybean in the second window), `semeaduras_validas[]` (sowing dates
  of the second crop for which the pair passes the calendar rules) and `motivo_se_invalida`.
- `rotacoes[]` (the same 22 ids with name and short description), `semeaduras`, `semeadura_padrao`, `criterios`, `pesos_padrao`,
  `renda_referencia` (prices, costs and `fontes[]`, with `estimativa` flagged), `regiao`, `talhoes_demo`.

`/talhoes/demo` returns only the `talhoes_demo` list.

### `GET /v1/culturas/fichas`

No inputs. Returns the agronomic crop sheets of `catalog/crops.yaml` (soybean, corn, wheat, white oat, barley, annual ryegrass), for
the frontend to show where each number comes from. Informative only: nothing here enters the score.

- `fichas[]`: one per crop, as in the catalog, plus `id`: `nome`, `nome_cientifico`, `finalidade`, `ciclo_dias`, `demanda_hidrica_mm_ciclo`,
  `requisitos_solo` (`texturas_adequadas`, `ph`, `nitrogenio`, `compactacao`, `umidade`), `infraestrutura`, `impactos_no_solo[]`,
  `vulnerabilidades[]`. Every numeric item is `{min, max, unidade, fonte}` (`fonte` is a URL: Embrapa, FAO Ecocrop, FAO-56); slugs
  (`valores`, `fases`, `efeito`, `risco`, `direcao`) stay as ids, free texts are translated with `?lang=en`.
- `mapeamento`: engine crop id -> sheet id (`null` = no sheet: millet/crotalaria, sorghum, beans, forage radish, fallow). Corn + brachiaria and
  oat + radish map to the corn and oat sheets (the sheet covers only that species).
- `fonte`: what the catalog is.

**Rotation, ids and catalog.** `verao`: `soja`, `milho_verao`. `segunda`: `milho_safrinha`, `milho_braquiaria`, `trigo`, `aveia`,
`milheto_crotalaria`, `pousio`, `soja_safrinha`, `sorgo`, `feijao_safrinha`, `nabo_forrageiro`, `aveia_nabo`. The id is
`"<verao>__<segunda>"` (e.g. `soja__milho_safrinha`, `milho_verao__aveia_nabo`). The old slugs are still accepted in `rotacao_atual` and
`restricoes.culturas_excluidas` and mean soybean in summer (`milho_safrinha` = `soja__milho_safrinha`; only the original 7); in responses the
`id` is always the new one and `id_legado` holds the old slug (null for the new rotations). `rotacao_detectada.rotacao` (in `/diagnostico`) still
returns the old slug.

**Calendar and legal rules** (they eliminate the rotation, with a readable reason in `eliminadas`):

- Soybean in the second window is always eliminated: it falls outside the soybean sowing window and inside the soybean-free period of the
  municipality's ADAPAR region (Portaria SDA/MAPA 1.579/2026: Região 1 sowing 20/09–20/01, void 21/06–19/09; Região 2, which includes the Oeste,
  01/09–31/12 and 02/06–31/08; Região 3 11/09–10/01 and 12/06–10/09) and, after soybean, it would be soybean after soybean (prohibited).
  This also applies after `milho_verao`.
- The second crop that follows the chosen sowing date (off-season corn, corn+brachiaria, sorghum, beans, millet/crotalaria) can only be sown
  after the summer harvest of the **current** summer crop. With `estagio_verao` or `colheita_prevista` that harvest is the estimated one; without them it is
  the catalog assumption (soybean ~10/01, summer corn ~05/02; estimates, to be validated). A harvest after the last sowing date considered (15/03) is
  "too late" (`semeadura_2a` null, warning in `avisos`): those crops are eliminated and only the fixed-date ones (wheat, oat, radish, fallow) stay.
  The same estimated harvest applies to the summer crop of every candidate in the same response, which is why summer corn followed by those crops
  is eliminated at an early sowing date (see the known limitation at the end). Wheat, oat, radish and fallow have a fixed date and do not depend on the harvest.
- Off-season beans only accept sowing from 15/01 to 28/02, and sorghum from 15/01 to 15/03 (reference estimates based on ZARC/IDR-PR, to be validated).
- **Corn after corn** (`milho_verao` + `milho_safrinha` or `milho_braquiaria`) **is not eliminated**: the `pragas` criterion loses 0.25 points
  (corn leafhopper/corn stunt, fall armyworm; estimate), and the text goes into `card.riscos` and `card.evidencias`.
- **Summer corn instead of soybean** adds a 3 bags/ha bonus on the following soybean (breaks the disease and nematode cycle, plus straw; reference
  estimate to be validated), in addition to the second crop's straw/N bonus.

**Summer income.** The rotation margin is summer + second crop + bonus. The score uses the increment over the municipality's summer soybean:
`incremental = rotation margin − soybean margin`, `renda = 0.5 + 0.5·tanh(incremental / S)`, with S = BRL 1,110/ha in all of Paraná (see `renda` in "How the score is computed" below).
With soybean in summer the formula is the usual one; summer corn enters with PAM 1st-season corn × DERAL corn price − CONAB 1st-season corn cost
(Ponta Grossa-PR, the only current Paraná sheet; it uses a reference yield of 12 t/ha, above Western Paraná's, so the summer-corn margin tends to be underestimated).
The summer crop does not enter the water and climate-risk criteria (only the second window does).

### `GET /v1/contexto` and `POST /v1/contexto`

**Current conditions** layer: queries official sources about ongoing events and returns them as context. **It forecasts nothing and does not change
the ranking or the score** (the recommendation does not depend on it and never fails because of it). `GET`: query `talhao_id` **or** `lat`+`lon`,
`semeadura_safrinha` (default `01/02`). `POST`: body `{"area": {...}, "semeadura_safrinha": "01/02"}` (also accepts `geometry`;
uses the centroid). Same errors as the recommendation (400, 422 `fora_da_regiao`). Latency: cold call up to ~40 s (SMAP); with cache, instant.

Each source comes in its own block with `disponivel`, `consultado_em` (UTC) and `fonte` (`nome`, `url`). If a source fails, only that
block becomes `{"disponivel": false, "motivo": "..."}` and the rest continues. Blocks:

| Block | Source | Cache | Content |
|---|---|---|---|
| `enso` | NOAA CPC (ENSO Diagnostic Discussion page + ONI table) | 24 h | `status_alerta`, `fase_atual`, `oni_ultimo`, `boletim.sinopse_original_en` (percentages cited by NOAA), `texto`; `historico_por_fase` (years 1991-2024 classified by the DJF ONI; per phase: `n_anos`, `anos_com_evento`, `frequencia` of off-season dry spell, off-season frost at the chosen sowing date and wheat frost, plus `frequencia_media_geral`) and `frases_historico` |
| `smap` | NASA SMAP L4 (SPL4SMGP v8), ~9 km pixel, via Earthdata (`~/.netrc`) | 24 h | `atual` (root-zone and surface moisture, `sm_rootzone_pctl` = percentile in the SMAP climatology), `classe` (below/normal/above), `ha_7_dias`, `tendencia_7d_percentil`. Product latency: 2 to 3 days |

| `pragas.ferrugem_soja` | IDR-PR, public WFS of the State GeoServer (automatic) | 24 h | collectors with/without spores in the municipality, in the Western mesoregion and within a 100 km radius, in the current season |
| `pragas.alertas_curados` | `data/contexto/pragas_alertas.json` (curated by hand: corn leafhopper and other ADAPAR/IDR-PR alerts) | read on every call | current alerts per region, with text attributed to the source; `como_consultar` with links (CigarrinhaWeb, ADAPAR) |

## How the score is computed

The score of each rotation (0 to 1 scale, with every criterion on an absolute 0 to 1 scale) is the **weighted average** of the 5 criteria by the `pesos`:
`nota = sum(weight_i x criterion_i) / sum(weight_i)`. The `contribuicoes` field shows how much each
criterion weighed, and `metodologia.formula` gives the exact formula of the running version. Default weights: income 5, others 3. The detailed engine logic is in [`docs/motor.md`](../docs/motor.md).

| Criterion | Origin |
|---|---|
| `renda` | **Incremental** margin of the second season (BRL/ha) = yield (municipal IBGE PAM) x price - cost (SEAB/DERAL, CONAB) of the second crop (cover/fallow: - cost) + straw/N bonus on the following soybean; soybean, common to all, is left out. For off-season corn, corn + brachiaria and wheat the second-crop margin is the mean realized margin of the last 5 seasons in the municipality (better out of sample than the current-price estimate; `docs/validation.md` §6.2), unless the farmer typed price, cost or yield for that crop. Score = `0.5 + 0.5·tanh(incremental / S)`, with S = BRL 1,110/ha in all of Paraná (median soybean margin of the Oeste municipalities; it was each municipality's soybean margin until `docs/validation.md` §7.5): zero = 0.5; +S = 0.88; -S = 0.12 (never saturates). `margem.total_r_ha` (soybean + incremental), `incremental_r_ha` and `escala_S_r_ha` appear in the ranking; `ano_ruim_r_ha` shows the adverse scenario |
| `solo` | SoilGrids (texture, organic matter), effect of cover/straw and of brachiaria/legumes; terrain (NASADEM) for erosion |
| `agua` | NASA POWER: precipitation - ET0 balance, rain onset, off-season dry spell |
| `pragas` | Crop history (MapBiomas) and pest/disease cycle break by the rotation |
| `risco` | NASA POWER: probability of frost (by sowing date) and of water deficit in the critical phase (FAO-56 balance; dry spell when there is no soil), heat for soybean |

**Hard rules (they eliminate the option, with no score):** the soybean-free period (02/06 to 31/08), the soybean
planting window (01/09 to 31/12) and the prohibition of soybean after soybean. Vetoed options appear in
`eliminadas[]` with the reasons.

**What is an estimate:** yield (municipal PAM average, not the field's), margins and prices
(regional references; use `ajustes` with the real values), agronomic effects on soil and pests
and the rotation detected from the satellite history. They must be validated with the agronomist; ZARC
remains the reference for rural credit.

## Errors and HTTP codes

| Code | `erro` | When |
|---|---|---|
| 200 | n/a | Success |
| 400 | `entrada_invalida` | The engine rejected the input (invalid geometry, nonexistent field, area above 5000 ha, restrictions that eliminate every rotation, etc.) |
| 422 | n/a (`detail[]`) | Per-stage flow: missing `rotacao_atual`; `estagio_verao` that does not belong to the current summer crop (e.g. a corn stage with soybean) or is unknown; malformed `colheita_prevista` or `data_referencia`; `semeadura_safrinha` before the estimated harvest |
| 422 | n/a (`detail[]`) | An unknown key in `ajustes.custos`/`precos`/`produtividade`, a negative value, `analise_solo` out of range (sand + clay > 100, pH, available water capacity) or incomplete, `irrigacao` without `disponivel`, etc. are also rejected by validation |
| 422 | `fora_da_regiao` | The area is outside Paraná |
| 422 | n/a (FastAPI default format, `detail[]`) | Invalid body/parameters: out-of-enum sowing date, weight outside 0 to 10, unknown rotation, empty, duplicated or out-of-enum `rotacoes`, `n_alternativas` outside 1 to 6, an area with zero or more than one form |
| 500 | `interno` | Unexpected failure (the detail is only in the server log) |

Engine errors have the format `{"erro": "...", "mensagem": "..."}`. With `lang=en` the `mensagem` is in English and `erro` stays the same code.

## Limitations

- Climate comes from NASA POWER, on a ~50 km grid: neighboring fields share the same cell.
- Yield, margins, agronomic effects and the detected rotation are **estimates** to be validated.
- Reference prices and costs come from CONAB (Londrina for soybean and off-season corn, Ponta Grossa for wheat and summer corn, Francisco Beltrão for beans) and SEAB/DERAL; use `ajustes` for the real values.
- Without an official source, the values are estimates marked "estimate — to be validated" in `data/ref/precos_custos.json`: sorghum price (75% of DERAL corn, the CONAB 2026/27 minimum-price ratio),
  sorghum cost (CONAB sheet for Rio Verde-GO; there is none for Paraná) and the cost of forage radish, oat + radish, oat, millet/crotalaria, brachiaria and fallow.
  Also estimates: Kc and critical phase of the new crops, sowing windows, summer harvest dates, rotation bonus and the corn-after-corn penalty.
- Maximum area per request: 5000 ha.
- Farmer data inputs: outsourcing costs, irrigation cost/depth and market levels per crop are estimates to be validated. Irrigation does not raise the expected yield. The soil analysis (default 0 to 20 cm) is taken as representative of the whole root profile.
- Full example: `api/exemplos/recomendacao_dados_proprios.json` (field 72638 with yield, soil analysis, restrictions and irrigation).
- Coverage of Paraná only. **Outside the Oeste mesoregion**, costs and prices (SEAB/DERAL, CONAB) are the Oeste references and the response carries a warning in `avisos` saying so, plus a second one with the statewide validation finding (the cover crop ranks first more often outside the Oeste but lost to off-season corn on realized income in every mesoregion; the card states the income given up when the first is not the highest-income option; `docs/validation.md` §7). The soybean calendar is regional: the municipality's ADAPAR region decides the sanitary void and the sowing window (Portaria SDA/MAPA 1.579/2026, crop 2026/2027: Região 1 void 21/06–19/09 and sowing 20/09–20/01; Região 2 void 02/06–31/08 and sowing 01/09–31/12; Região 3 void 12/06–10/09 and sowing 11/09–10/01), and outside the Oeste a third `avisos` entry quotes the region and dates used. The windows live in `data/ref/vazio_sanitario_pr.json` (built by `ingest/soybean_free_period_pr.py`) and must be refreshed every April when MAPA publishes the new portaria. Confirm the current ADAPAR ordinance and the municipality's ZARC. ZARC remains the reference for rural credit.
- Endpoints are synchronous and the first call can be slow (loading rasters and data).
- Stage durations (days to harvest per stage) and the catalog harvest dates are estimates, to be validated with Embrapa/an agronomist.
- **Known limitation (open decision):** the `proxima_safra` block uses the same second-window sowing date as `agora` (derived from the current harvest). Summer corn in the next season would be harvested later (~05/02), so with that date summer corn followed by off-season corn, corn+brachiaria, millet/crotalaria, sorghum or beans is eliminated, and the block ends up with only the fixed-date crops (wheat, oat, radish, fallow). The alternative (computing the next season's sowing with the typical summer-corn harvest) was not decided yet; see `docs/pendencias.md`.
